# Security — Cloud Ops AI Intelligence

V1 of this system is deliberately constrained to eliminate an entire category of risk:
**it cannot act on real infrastructure, because it never connects to real infrastructure.**
This document defines the rules that keep that guarantee true through implementation.

## 1. Core guarantees (V1)

1. **Simulated data only.** No component connects to a real cloud account, real
   Kubernetes cluster, or real log/metrics backend. All telemetry is fixture data checked
   into the repo or generated by a local simulator.
2. **Read-only.** No tool available to any agent can issue a mutating call (create,
   update, delete, scale, restart, patch) against any infrastructure API — simulated or
   real. Agents only read/analyze data that's handed to them.
3. **No production credentials.** No cloud account credentials, kubeconfig for a real
   cluster, or production secrets exist anywhere in this repo, its configuration, or its
   runtime environment. The only real external credential in V1 is the OpenAI API key.
4. **No automatic remediation.** The Remediation Advisor Agent produces text
   recommendations only. There is no tool, function, or integration anywhere in the system
   capable of executing a remediation action. This is enforced architecturally (no such
   tool is ever defined), not just by prompting the agent to refrain.

These guarantees are re-verified against docs/agent-design.md's "Boundaries checklist"
during implementation review.

## 2. Secrets management

- The only secret V1 requires is the OpenAI API key.
- Secrets are supplied via environment variables / a local `.env` file, never hardcoded.
- `.env` and any file containing real secrets must be listed in `.gitignore` and never
  committed. A `.env.example` with placeholder values may be committed instead.
- No secret is ever logged, included in an LLM prompt/response that gets persisted, or
  written into a fixture file.

## 3. Data handling

- Simulated fixture data (logs, cloud state, K8s state, runbooks) must not contain real
  customer data, real employee data, or any real identifiers — it is synthetic by
  construction.
- Data sent to the OpenAI API is limited to the incident investigation context (fixture
  data, task outputs). No secrets, and no data beyond what's needed for that task's stated
  responsibility, should be included in any prompt.
- The ChromaDB knowledge store holds only simulated runbooks/past-incident write-ups
  authored for this project — not real incident data — unless the user explicitly decides
  to change this in a future phase.

## 4. API & access (FastAPI / Next.js)

- The FastAPI backend, once implemented, exposes read/trigger-investigation endpoints only
  — no endpoint accepts or forwards a remediation/execution request.
- Basic authentication/authorization on the FastAPI backend is required before any
  non-local deployment; exact mechanism (API key, session auth, etc.) is decided at
  implementation time and documented here when chosen.
- CORS is restricted to the known Next.js frontend origin(s); no wildcard origins in
  non-local environments.
- The Next.js frontend never talks directly to OpenAI, ChromaDB, or any fixture data — it
  only calls the FastAPI backend.

## 5. Dependency and tool hygiene

- No new dependency is added without checking it against CLAUDE.md's "do not install
  unnecessary dependencies" rule.
- Any CrewAI "tool" given to an agent must be reviewed against this document before being
  added — specifically: does it read only, does it touch only simulated data, and does it
  avoid any credential that could reach a real system.
- Third-party packages are pinned in dependency files once implementation starts, to avoid
  unreviewed transitive changes.

## 6. Audit and traceability

- Each investigation run should be traceable: which agent produced which finding, which
  task outputs fed the root-cause synthesis, and what the final report contained (see
  docs/evaluation.md, docs/requirements.md §4 "Auditability").
- This traceability is a safety property as much as a quality one — it's what lets a human
  verify that a recommendation is grounded in real evidence before acting on it.

## 7. Threat model summary (V1)

| Threat | Mitigation |
|---|---|
| Agent hallucinates a remediation and something executes it | No execution capability exists anywhere in the system |
| Real credentials get committed or referenced | No real infra credentials in scope for V1; `.env` gitignored; only the OpenAI key is real |
| Prompt injection via fixture/log content influences an agent into recommending a harmful action | Even if it does, no tool exists to execute anything — worst case is a bad line in a report reviewed by a human |
| Sensitive data leaks into OpenAI prompts | Fixture data is synthetic by construction; no real customer/employee data enters the system in V1 |
| Unauthorized access to the FastAPI backend | Auth required before any non-local deployment (§4) |

## 8. Path to production (explicitly future work, not V1)

Any future move beyond simulated/read-only — real cloud/K8s read access, real remediation
execution, real production credentials — is a distinct phase requiring its own explicit
scoping, review, and sign-off from the user. Nothing in V1's implementation should assume
or silently prepare for that transition (e.g., no "TODO: swap in real API here" stubs that
make it easy to accidentally point at production).
